\# 智护库安 - 微型水上自主搜救演示艇项目文档



\## 一、项目概述



在 1.2m × 1.2m 微型水池中，模拟“人员落水 → 系统识别 → 船自主出发 → 抵达目标 → 精准投放”的完整自主搜救演示。



核心设计哲学：\*\*电脑做全局决策，船载视觉做局部瞄准，主控做底层执行。\*\*

\### 3.2 通信协议



\*\*电脑 → 船（GroundToBoat，26 字节）\*\*



| 字段 | 类型 | 含义 |

| :--- | :--- | :--- |

| boat\_x | float | 船当前 X 坐标（米） |

| boat\_y | float | 船当前 Y 坐标（米） |

| boat\_heading | float | 船当前航向（0-360°） |

| target\_x | float | 目标 X 坐标（米） |

| target\_y | float | 目标 Y 坐标（米） |

| mission\_state | uint8 | 0=待命, 1=自主航行, 2=释放, 3=返航, 4=手动遥控 |

| release\_flag | uint8 | 0=不释放, 1=释放 |

| manual\_throttle | int16 | 手动油门 -255\~255 |

| manual\_steer | int16 | 手动转向 -255\~255 |



\*\*船 → 电脑（BoatToGround，32 字节，C 结构体对齐）\*\*

`GroundToBoat` 在两端固件中使用 packed 布局，固定为 26 字节；`BoatToGround` 保持 ESP32 C 结构体对齐，固定为 32 字节。两端启动时会打印实际 MAC 和信道，且只有白名单 MAC 的帧会被接受。



| 字段 | 类型 | 含义 |

| :--- | :--- | :--- |

| boat\_heading | float | 船当前航向 |

| left\_motor\_speed | int | 左电机 PWM |

| right\_motor\_speed | int | 右电机 PWM |

| target\_detected | uint8 | 二哈是否检测到目标 |

| local\_target\_x | int | 目标画面 X 坐标 |

| local\_target\_y | int | 目标画面 Y 坐标 |

| estimated\_dist\_m | float | 二哈估算距离（米） |

| emergency\_mode | uint8 | 是否处于应急模式 |



\*\*Python 打包格式\*\*：

```python

\# 电脑→船

GROUND\_TO\_BOAT\_FORMAT = '<fffffBBhh'  # 26 字节



\# 船→电脑（含 padding）

BOAT\_TO\_GROUND\_FORMAT = '<ffiBxxxiiifBxxx'  # 32 字节

```



\### 3.3 通信逻辑



| 情况 | 桥接板行为 | DFR1063 行为 |

| :--- | :--- | :--- |

| 电脑发指令 | 立即 ESP-NOW 转发 | 更新 lastRecvTime，执行任务 |

| 电脑无指令 | 每 50ms 轮询发上次指令 | 刷新 lastRecvTime，保持当前任务 |

| 桥接板断电 | 停止发送 | 超过 3 秒未收到 ESP-NOW 数据后进入应急搜索；二哈未发现目标时原地转圈，发现后追踪并在估算距离不大于 20cm 时停车 |

| 桥接板恢复 | 重新轮询 | 退出应急，恢复电脑控制 |



\### 3.4 控制频率



| 任务 | 频率 |

| :--- | :--- |

| 主循环 | 20Hz (50ms) |

| 二哈 I2C 读取 | 10Hz (100ms) |

| 调试输出 | 2Hz (500ms) |

| ESP-NOW 上报 | 20Hz |



\### 3.5 上位机 Python 功能



1\. \*\*鼠标点击四个角\*\*完成水池标定，计算单应性矩阵 H

2\. \*\*ArUco 识别\*\*：识别船顶 ID 0 码，计算船位置 `(boat\_x, boat\_y)` 和航向 `boat\_heading`

3\. \*\*颜色检测\*\*：HSV 阈值分割目标，取轮廓底部中心点作为水面接触点，映射为目标坐标 `(target\_x, target\_y)`

4\. \*\*距离计算\*\*：`sqrt((target\_x-boat\_x)² + (target\_y-boat\_y)²)`

5\. \*\*串口发送\*\*：打包 `GroundToBoat` 发给桥接板

6\. \*\*状态接收\*\*：解析 `BoatToGround`，实时显示船的状态

\## 四、操作逻辑



\### 4.1 完整任务流程



1\. \*\*人员落水\*\*：水池中放入模拟落水者（橙色浮球/红色浮板，需露出水面）

2\. \*\*全局监控\*\*：UVC 相机拍摄整个水池，电脑识别船顶 ArUco 码和目标颜色

3\. \*\*任务下发\*\*：电脑通过桥接板 ESP-NOW 发送船坐标、目标坐标、任务状态

4\. \*\*船出发\*\*：DFR1063 计算期望航向，PID 差速控制双明轮前进

5\. \*\*坐标导航与末端微调\*\*：先按电脑下发的船/目标坐标导航；进入目标 40cm 范围后切换到二哈视觉，锁定目标并做近距离追踪

6\. \*\*精准停靠\*\*：二哈估算目标距离不大于 20cm 时停船；末端阶段未检测到目标时停车等待重新识别

7\. \*\*投放\*\*：电脑发“释放”指令，MG90S 舵机拉动插销，投下救生圈

8\. \*\*返航/待命\*\*：电脑可下发返航或待命指令



\### 4.2 三种工作模式



| 模式 | mission\_state | 行为 |

| :--- | :--- | :--- |

| 待命 | 0 | 电机停止 |

| 自主航行 | 1 | 先按电脑坐标导航；进入目标 40cm 范围后由二哈精细追踪，估算距离不大于 20cm 时停车 |

| 释放 | 2 | 停船 + 舵机释放 |

| 返航 | 3 | 返回起点 |

| 手动遥控 | 4 | 电脑直接控制油门和转向 |



\### 4.3 应急逻辑



\- \*\*触发条件\*\*：桥接板断电或死机，DFR1063 超过 3 秒未收到 ESP-NOW 数据

\- \*\*行为\*\*：

&#x20; - 二哈看到目标 → 追踪目标，估算距离不大于 20cm 时停车

&#x20; - 二哈没看到目标 → 原地慢速旋转搜索

\- \*\*恢复\*\*：收到桥接板数据后自动退出应急，恢复电脑控制



\### 4.4 安全机制



| 机制 | 说明 |

| :--- | :--- |

| 电机安全使能 | `ENABLE\_MOTOR\_OUTPUT = false` 时电机强制不转，陆地调试安全 |

| 调试输出节流 | `ENABLE\_DEBUG = false` 时串口静默，提高主循环速度 |

| 通信超时保护 | 3 秒无桥接板数据进入应急搜索；重新收到桥接板指令后退出应急 |

| 低压报警 | 2S LiPo 放到 6.8-7.0V 必须返航 |

| 舵机供电隔离 | UBEC 5V 独立供电，不占用主控板载 5V |

| 电源去耦 | 1000μF 电容吸收电机启停电压波动 |

\## 六、关键工程注意事项



1\. \*\*二哈必须独立供电\*\*：通过 Type-C 接 UBEC 5V，不能只靠 I2C 3.3V 漏电流

2\. \*\*MAC 地址互填正确\*\*：桥接板填 DFR1063 的 MAC，DFR1063 填桥接板的 MAC

3\. \*\*信道一致\*\*：两端使用 `esp_wifi_set_channel(1, WIFI_SECOND_CHAN_NONE)` 强制到信道 1，并在启动日志中打印实际信道

4\. \*\*I2C 共地\*\*：二哈 GND 必须和 DFR1063 GND 相连

5\. \*\*电机消噪\*\*：0.1μF 电容焊在电机引脚上

6\. \*\*电源去耦\*\*：1000μF 电容并联在 UBEC 5V 输出端

7\. \*\*Type-C 调试口下水时拔掉\*\*：下水跑船完全靠电池供电

8\. \*\*ArUco 码留白边\*\*：打印时四周至少留 1cm 白边，否则识别失败

9\. \*\*目标不能贴标记\*\*：用颜色/轮廓识别，目标需露出水面且与水面对比明显

10\. \*\*PID 参数需实测调整\*\*：起步 `Kp=2.0, Ki=0, Kd=0.5`，船左右摇摆则降 Kp 或加 Kd

### 3.6 Web 驾驶控制台（v1.1）

新增基于 React + Vite 的本地驾驶页面：

- 从 `Software/boat-rescue-console/` 运行 `npm run dev` 同时启动网页和本地串口/WebSocket 服务，默认访问 `http://127.0.0.1:5173`。
- 当前设备串口映射：`COM10` 是船载 ESP32-C3/DFR1063 主控，桥接板为 **Waveshare ESP32-S3-LCD-1.47**（USB-Serial-JTAG，端口号会随枚举变化，实测为 `COM12`）；网页默认连接桥接板端口，波特率 115200。
- **串口选择已改为自动识别**（不再写死 COM11）：服务端 `/api/ports` 会过滤掉蓝牙虚拟串口，并给每个 Espressif 设备打 `isEspressif` 标记；网页在**只有一个 ESP32 设备时自动选中**它。
  > 限制：桥接板(ESP32-S3)与船载主控(ESP32-C3)的 USB VID/PID **完全相同**（`303A:1001`），驱动层无法区分二者。因此当两个设备同时接入时，网页会显示提示要求人工指定桥接板端口（连错船载主控不会报错，但没有任何遥测）。
- 手动模式使用 WASD 按住控制、松开归零；自主模式填写船体 X/Y、航向和目标 X/Y，点击“开始自主导航”后桥接板以 `mission_state=1` 持续转发坐标。空格、失焦、断开连接均锁定动力并发送中立指令。
- 水池坐标范围为 0–1.2m，航向为 0–360°。主控没有罗盘或全局定位传感器，船体坐标和航向必须由上位机定位持续更新；当前页面提供手动录入，UVC 相机定位尚未实现，静态输入只适合短时台架验证，不构成完整的闭环自主航行。
- 视频通过 Janus WebRTC 接收 `http://192.168.2.14:8088/janus` 上的 Streaming 流 ID 99。
- 本地服务只监听 `127.0.0.1:4174`，负责串口枚举、命令超时归零和遥测转发。
- 串口协议使用 `A5 5A + 26 字节 GroundToBoat + 1 字节累加校验`；回传使用 `5A A5 + 32 字节 BoatToGround + 1 字节累加校验`。

桥接板连续 300ms 未收到电脑命令时将待发命令切回待机并将油门、转向归零；船载主控收包前检查长度，通信超时默认停车，不进入自动巡航。电机输出在固件中启用，首次下水前应先在抬轮状态验证电机方向、急停及串口失联停车。当前主控没有罗盘/IMU，网页对船头航向显示“---”，不使用电脑下发的期望方向冒充实际航向。

### 3.7 固件工程（v1.2：两端统一为 ESP-IDF）

桥接板与船载主控的固件已从 Arduino 迁移到 **ESP-IDF v6.1**，与网页端形成统一工具链：

| 工程 | 位置 | 目标芯片 | 说明 |
| :--- | :--- | :--- | :--- |
| 桥接板 | `Hardware/Firmware/boat/bridge-idf/` | ESP32-S3 | USB 串口 ↔ ESP-NOW 透传，**新增状态屏显示链路与船端遥测** |
| 船载主控 | `Hardware/Firmware/boat/controller-idf/` | ESP32-C3 | 电机/舵机/二哈/ESP-NOW/PID 导航 |

原有 `Hardware/Firmware/boat/arduino-reference/` 目录保留，作为 Arduino 版参考实现，两者协议完全兼容。

**共用配置**：`Hardware/Firmware/boat/arduino-reference/boat_config.h` 是 MAC/信道的**唯一数据源**，三个固件都通过相对路径引用它，避免"改一处漏一处导致 ESP-NOW 不通"。

**桥接板状态屏**（320×172 横屏，LVGL 8.3）显示：

- `PC LINK` 串口链路状态与命令计数
- `ESPNOW TX` 发送成功/失败计数（**fail 不为 0 即表示船端未应答**）
- `BOAT RX` 船端回传静默时间与接收计数
- `MOTOR L/R`、`TARGET`、`DISTANCE` 船端遥测

**船载主控相对 Arduino 版的三处改进**：

1. **投放舵机真正实现**：Arduino 版 `releasePayload()` 中舵机代码被注释、`Servo` 对象从未创建，投放功能实际缺失。ESP-IDF 版补齐 MG90S 驱动（GPIO6，50 Hz），并做成**非阻塞状态机**（拉出 → 保持 500 ms → 回位），避免 `delay(500)` 阻塞主循环导致丢帧。
2. **差速控制归一化**：Arduino 版分别对左右轮 `constrain(0,180)`，当航向误差较大时一侧饱和到 0、另一侧到 180，PID 失去控制律。改为按比例整体缩放，保留差速比例。
3. **HUSKYLENS 2 驱动自实现**：不移植依赖 Arduino `String`/`Stream`/`TwoWire` 的官方库，而是按官方协议文档直接实现最小子集（`55 AA | CMD | AlgoID | Len | Data | 校验`，校验为从首字节累加至数据末尾取低 8 位）。I2C 传输为裸读裸写，不发寄存器地址。

**编译与烧录**：

```powershell
# 桥接板（ESP32-S3，实测 COM12）
cd Hardware/Firmware/boat/bridge-idf;     . .\idf-env.ps1; idf.py -p COM12 flash monitor

# 船载主控（ESP32-C3，实测 COM10）
cd Hardware/Firmware/boat/controller-idf; . .\idf-env.ps1; idf.py -p COM10 flash monitor
```

`idf-env.ps1` 用于准备 EIM 安装的 IDF 环境（需设 8 个环境变量，缺失 `ESP_IDF_VERSION` 会导致 `idf.py` 直接崩溃）。

> 注意：两个 `idf-env.ps1` 里的 `IDF_PATH` 指向 `F:\esp\v6.1\esp-idf`，换机器需同步修改。

### 3.8 HUSKYLENS 2 驱动实现要点（踩坑记录）

船载固件没有移植官方 `DFRobot_HuskylensV2` 库（其依赖 Arduino `String`/`Stream`/`TwoWire`），而是按协议文档自实现最小子集。实测中确认了以下几点，改动时务必保留：

1. **二哈会主动发心跳帧**：命令号 `0x1A`、数据含一个 IEEE754 浮点 + 4 字节计数器，约每 150 ms 一帧。
   → 因此**不能用"收到任意完整帧"判定应答**，必须按命令号匹配。最初就是被心跳误导，把 `s_ready` 错误置位后握手永远失败。
2. **握手/切算法需要重试**：二哈有启动时间，且刚握完手可能尚未准备好接收下一条命令。实测单次发送经常失败，需要"延时 + 重试"（官方库 `retry=5`）。
3. **I2C 出错不会自行恢复**：一旦出现异常，后续调用会持续返回 `ESP_ERR_INVALID_STATE`（实测运行十几秒后进入此状态）。
   → 固件在检测到传输错误时**删除并重建 I2C 总线**，重建后重新握手。已实测验证可恢复。
4. **运行期重试连接**：二哈可能比主控晚就绪，启动窗口内读到全 `0xFF`（从机未驱动总线）。固件在主循环中每 2 秒重试一次连接，就绪后自动切换算法。
5. **协议格式**（与库源码逐字节核对）：
   ```
   帧: [0]=0x55 [1]=0xAA [2]=CMD [3]=AlgoID [4]=Len [5..]=Data [5+Len]=校验
   校验: 从 [0] 累加到 [4+Len]（不含校验字节），取低 8 位
   I2C 传输: 写=按 16 字节分包；读=裸读 16 字节，不发寄存器地址
   ```

**实测验证结果**（2026-10 于本机）：

```
I BOAT_HUSKY: HUSKYLENS 2 握手成功
I BOAT_HUSKY: 切换算法 3 成功
I BOAT_MAIN:  [状态] 待命 | 二哈:有目标 | 遥控 159/0 | 释放 0
I BOAT_MAIN:         目标 X=272 Y=156 宽=289 估算距离=0.17 m
```

目标坐标、像素宽度与单目测距均已正确解析。

> 投放释放（舵机）另见 §3.10。

### 3.9 全局视觉定位（上位机，`Software/boat-rescue-console/vision/`）

补上了原文档 §3.5 里"上位机 Python 功能"的实现。现在**完整自主链路已可用**：

```
顶端 UVC 相机 → Software/boat-rescue-console/vision/locator.py（ArUco + 颜色检测）→ 水池米坐标
   → HTTP POST /api/navigation → Software/boat-rescue-console/serial-service/index.js → 26 字节帧 → 串口
   → 桥接板 → ESP-NOW → 船载主控 → 坐标导航 → 40cm 内二哈接管 → 20cm 停车
```

**为什么坐标走 HTTP 而不是直接用 pyserial 发串口**：串口同一时刻只能被一个进程占用。若 Python 直接持有串口，网页就无法连接、也看不到遥测。改为喂给 Node 服务后：

- 网页与视觉程序**可同时运行**，互不干扰
- 视觉停推 **400 ms** 内自动把控制权交还网页
- 串口只由 Node 服务持有，避免争抢

**文件说明**：

| 文件 | 职责 |
| :--- | :--- |
| `Software/boat-rescue-console/vision/locator.py` | 主程序：`--calibrate` 标定 / 默认实时定位 / `--simulate` 无相机验证 |
| `Software/boat-rescue-console/vision/pool.py` | 水池标定与单应性变换（像素 ↔ 米） |
| `Software/boat-rescue-console/vision/boat.py` | ArUco 检测 → 船坐标 + 航向 |
| `Software/boat-rescue-console/vision/target.py` | HSV 颜色分割 → 目标坐标（取轮廓底部中心点） |
| `Software/boat-rescue-console/vision/pick_hsv.py` | 现场取色工具，鼠标点击测 HSV 阈值 |
| `Software/boat-rescue-console/vision/config.py` | 相机参数、ArUco ID、HSV 阈值、上报频率 |

**使用步骤**：

```powershell
pip install -r Software/boat-rescue-console/vision/requirements.txt

cd Software/boat-rescue-console/vision
python locator.py --calibrate     # 鼠标依次点水池四角：左下→右下→右上→左上
python pick_hsv.py                # 鼠标点选目标，取 HSV 阈值填进 config.py
python locator.py                 # 正式定位（保持 npm run dev 在运行）
python locator.py --simulate      # 无相机：用运动学模型验证整条链路
```

**坐标系与航向约定**（与船端 PID 必须一致）：

- 水池坐标：标定四点决定，左下为原点，X 向右、Y 向上，量程 1.2 m
- 航向：`0°` 指向 `+Y`，顺时针为正（对应船端 `atan2(dx, dy)`）

**⚠️ 航向精度是整个系统最脆弱的一环**：

俯视相机里 5 cm 的 ArUco 码只有几十像素，角点抖动 1~2 px 就会带来数度航向误差，而船端 PID **直接把它当 `boat_heading` 用**。航向噪声大 → PID 持续振荡 → 船在目标点附近绕圈（这类系统最典型的失败模式）。

代码里已做三重缓解：角点按 `x+y`/`y-x` 排序保证顺序稳定、方向向量取两侧边平均、航向低通滤波（`HEADING_SMOOTHING=0.4`）。若实测仍振荡：

1. 把 ArUco 码**印大一些**（10 cm 优于 5 cm）——最有效的办法
2. 降低 `HEADING_SMOOTHING`（更平滑但更滞后）
3. 降低船端 PID 的 `Kp` 或加大 `Kd`

**⚠️ HSV 阈值必须现场标定**：相机白平衡、灯光色温、水面反光都会改变 HSV，同一组阈值换房间或换时段就可能失效。务必用 `pick_hsv.py` 实测。

**已知限制**：

- 相机镜头畸变若不做去畸变，水池边缘区域的航向误差会被放大
- 水面波纹会让 ArUco 角点抖动，建议码贴平、避免贴在反光面上
- 颜色识别在强反光/水花条件下会误检，必要时改用 YOLO（原文档 §8 待办）

### 3.10 投放释放（v1.4 补齐）

原 Arduino 版的 `releasePayload()` 里舵机代码是注释掉的、`Servo` 对象从未创建，
`release_flag` 在网页端也被硬编码为 0 —— 也就是说**"精准投放"这一环原本是空的**。
现已补齐三处：

| 环节 | 改动 |
| :--- | :--- |
| 船端固件 | MG90S 驱动（GPIO6，50 Hz）+ **非阻塞状态机**（拉出 → 保持 500 ms → 回位） |
| 协议 | `encodeGroundToBoat` 支持 `overrides`，可强制 `mission_state=2` / `release_flag=1` |
| 服务端 | WebSocket `{type:'release'}` → 200 ms 时间窗内持续下发释放帧，之后自动恢复原模式 |
| 网页 | 「投放释放」面板 + 二次确认（3 秒内未确认自动取消） |

**关键设计说明**：

1. **释放期间强制停船**：`mission_state=2` 时协议层把油门/转向写 0，避免"边冲边投"。
2. **为什么用 200 ms 时间窗而不是发一帧**：串口帧可能丢失，而投放失败意味着整个救援
   任务失败；多发几帧保证送达。重复触发由船端"动作进行中忽略"来防（舵机不会重复拉动）。
3. **不需要先解锁动力**：投放是救援动作本身的目的，且船端会自动停船，不冲突。
4. **舵机动作是非阻塞的**：用 `tick` 状态机推进，不用 `delay(500)` —— 否则会阻塞主循环
   500 ms，这段时间收不到 ESP-NOW 命令（原 Arduino 版写成注释里那种 `delay` 会有此问题）。

**⚠️ 未实现"释放次数回传"的原因**：`BoatToGround` 结构体必须**恰好 32 字节**才能与
Arduino 版逐字节兼容（`static_assert` 锁死）。该结构体无可用空隙（13-15、29-31 是编译器
隐式填充，不能当字段用），扩展它会破坏协议兼容性。因此**确认释放是否成功要看船端串口日志**：

```
I BOAT_SERVO: 释放机构动作：拉出插销 (90°)
I BOAT_SERVO: 释放完成，舵机回位
I BOAT_MAIN:  [状态] 释放 | ... | 释放 1        ← 末尾的"释放 N"是执行计数
```

**待实测**：MG90S 的机械动作（插销行程、弹簧复位）尚未在实机验证，首次测试建议脱开载荷、
确认舵机转向与行程是否匹配机构。

### 3.11 桥接板发热治理（实测数据）

桥接板接入后芯片发烫，实测结温 **78 °C**。通过一次隔离实验定位了热源归属：

**方法**：固件加 `DIAG_DISABLE_RADIO` 开关（`bridge-idf/main/main.c`），置 1 则不启动
WiFi/ESP-NOW，屏幕与诊断读数照常工作。这样能一刀切开"射频"与"其余部分"。

**实测结果**：

| 状态 | 芯片结温 | 差值 |
| :--- | :--- | :--- |
| 射频关闭 | **34.4 °C** | — |
| 射频开启（优化前） | **78 °C** | **≈ 44 °C 全部来自射频** |
| 射频开启（优化后） | **56.4 °C** | 射频部分压到约 22 °C |

**结论**：

1. **发热几乎全部来自射频**，与屏幕、背光、CPU、LDO 基本无关（这几项合计仅 34 °C）。
   因此"降背光 / 降像素时钟 / 降 CPU 频率"对温度帮助有限 —— 它们省电，但不是主因。
2. 射频成本主要是**"射频打开"本身的固有开销**（PLL 与模拟前端），而不是单次发射次数。
   把发送频率从 20 帧/秒降到 5 帧/秒几乎没降温，就是这个原因。
3. 因此**降发射功率的收益远大于降发送频率**。

**最终生效的三项优化**：

| 项 | 改动 | 位置 |
| :--- | :--- | :--- |
| 发射功率 | 20 dBm → **10 dBm** | `espnow_bridge.c` `ESPNOW_TX_POWER_QUARTER_DBM` |
| 发送频率 | 20 → **2 帧/秒** | `espnow_bridge.c` `SEND_INTERVAL_MS` |
| CPU 频率 | 160 → **80 MHz** | `sdkconfig.defaults` |

> ⚠️ **两个踩过的坑**（改这块代码时务必注意）：
>
> 1. `esp_wifi_set_max_tx_power()` **必须在 `esp_wifi_start()` 之后调用**，
>    放在之前会返回 `ESP_ERR_WIFI_NOT_STARTED` 并**静默失效** —— 第一版就是这样，
>    导致"温度没降"却查不出原因。现在代码里加了 `esp_wifi_get_max_tx_power()` 读回校验。
> 2. 诊断开关建好后**要确认真的改了值**。曾出现 `#define DIAG_DISABLE_RADIO 0` 而误以为
>    已置 1 的情况，结果拿到的"射频关闭"数据其实是射频开启的，差点得出错误结论。

**安全边界**：发送频率降到 2 帧/秒（500 ms）后，距船端 3 秒应急超时仍有 **6 倍余量**，
不会误触发应急模式。若现场距离远或丢包率高，把 `SEND_INTERVAL_MS` 调回 200 或 100。

**温度是否正常**：ESP32-S3 结温上限 85 °C（部分型号 105 °C）。结温通常比芯片表面高
15~25 °C，所以 56 °C 结温对应的表面温度约 35~40 °C，手感是温热。优化前 78 °C 属于
"偏高但未超限"，夏季室温上升会有风险 —— 这也说明当时处理是必要的。
